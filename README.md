# MiLog

MiLog is a Laravel 13 API for tenant-scoped event ingestion and timeline reads.

The current project focus is the public `v1` API:

- `POST /api/v1/events`
- `GET /api/v1/timeline`

This API uses:

- PHP 8.5
- Laravel 13
- PostgreSQL
- Redis
- Docker Compose
- API key authentication via `X-API-Key`

Older API surfaces are intentionally not described here.

## What It Does

MiLog provides an append-only event stream for SaaS applications that need a reusable timeline service.

Each event stores:

- tenant identity
- actor type and actor id
- action
- target type and target id
- log level
- arbitrary metadata
- occurred timestamp
- created timestamp

Timeline reads are tenant-scoped and support filtering by:

- `target_id`
- `actor_id`
- `type` where `type` matches `actor_type` or `target_type`
- `log_level` using viewer-facing levels

Responses also include a human-readable `message` generated by the formatter layer.

## Local Setup

Start the stack:

```bash
docker compose build
docker compose up -d
```

Run migrations:

```bash
docker compose exec -T milog-phpfpm php artisan migrate --force
```

The API is then available at:

```text
http://localhost:8980
```

## Provision a Tenant API Key

Create a tenant and issue a public API key:

```bash
docker compose exec -T milog-phpfpm php artisan milog:provision-tenant "Acme" --legacy-override
```

The command prints:

- tenant id
- API key id
- API key prefix
- the raw API key

Store the raw API key when it is shown. It is not persisted in plaintext.
This command is an administrative override for existing integrations. New
accounts should use the UI signup and credential flow described in
[docs/milog-ui-handover.md](docs/milog-ui-handover.md).

## Public API

### Authentication

Event ingestion requires a tenant-scoped API key:

```http
X-API-Key: YOUR_API_KEY
```

If the key is missing or invalid, the API returns:

```json
{
  "message": "Invalid API key."
}
```

Timeline reads also accept a tenant-bound UI access token. Keep producer API
keys in server-side applications and workers; do not put them in browser code.

### Create an Event

```bash
curl -X POST http://localhost:8980/api/v1/events \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -H "X-API-Key: YOUR_API_KEY" \
  -d '{
    "actor_type": "user",
    "actor_id": "42",
    "action": "created",
    "target_type": "invoice",
    "target_id": "inv_1",
    "log_level": "error",
    "metadata": {
      "source": "billing"
    },
    "occurred_at": "2026-05-01T22:00:00Z"
  }'
```

Required fields:

- `actor_type`
- `actor_id`
- `action`
- `target_type`
- `target_id`

Optional fields:

- `log_level`
- `metadata`
- `occurred_at`

If `log_level` is omitted, MiLog defaults it to `info`.
If `occurred_at` is omitted, MiLog sets it automatically.
Ingestion accepts `trace`, `debug`, `info`, `warn`, `error`, and `fatal` as
`log_level` values.
Metadata can be a JSON object or list; omitted or empty metadata currently
appears as `[]` in the response. Response timestamps use UTC ISO 8601 strings
and may include fractional seconds.

To retry a creation safely, send the same `X-Idempotency-Key` with the same
payload on every attempt:

```bash
curl -i -X POST http://localhost:8980/api/v1/events \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "X-Idempotency-Key: invoice-inv_1-created" \
  -d '{"actor_type":"user","actor_id":"42","action":"created","target_type":"invoice","target_id":"inv_1"}'
```

The first request returns `201` and the event. An identical replay returns
`200`, the same event, and `Idempotency-Replayed: true`. Reusing the key with a
different payload returns `409`. Keys are scoped to a tenant. Without a key,
repeated requests can create multiple events.

### Read the Timeline

```bash
curl "http://localhost:8980/api/v1/timeline?target_id=inv_1&type=user" \
  -H "Accept: application/json" \
  -H "X-API-Key: YOUR_API_KEY"
```

For a UI session, use `Authorization: Bearer ACCESS_TOKEN` instead of
`X-API-Key`. Event ingestion remains API-key-only.

Supported query parameters:

- `target_id`
- `actor_id`
- `type`
- `log_level`: a comma-separated list of `debug`, `info`, `success`,
  `warning`, and `error`
- `page`: offset pagination page number, starting at 1
- `pagination`: `offset` (default) or `cursor`
- `cursor`: opaque token from a cursor response; also selects cursor pagination

For example, `log_level=warning,error` matches stored `warn`, `warning`,
`error`, and `fatal` events. Selected levels use OR matching; other filters use
AND matching. The `info` filter also includes stored null and unrecognized
legacy levels. The ingestion and timeline filter level names are intentionally
different.

Results are ordered by:

1. `occurred_at` descending
2. `created_at` descending
3. `id` descending

Offset pagination includes `meta.current_page`, `meta.last_page`, and
`meta.total`. Cursor pagination has stable traversal when events are added and
returns `meta.next_cursor` and `meta.prev_cursor` instead of page numbers and
totals. Both modes include `data` and `links`. The default page size is 50.

```bash
curl "http://localhost:8980/api/v1/timeline?pagination=cursor&target_id=inv_1" \
  -H "Accept: application/json" \
  -H "X-API-Key: YOUR_API_KEY"
```

To continue, pass `meta.next_cursor` as the `cursor` query parameter with the
same filters, or follow `links.next`. A null next cursor/link means there are
no more events. Treat cursors as opaque strings; do not decode or construct
them yourself.

The API currently limits requests to 60 per minute and returns
`X-RateLimit-Limit` and `X-RateLimit-Remaining`. A `429` response contains
`{"message":"Too Many Attempts."}` plus `Retry-After` in seconds and
`X-RateLimit-Reset` as a Unix timestamp. Wait at least `Retry-After` before
retrying; reuse the same idempotency key and payload for an event creation.

## MiLog UI Authentication

The first-party UI uses tenant-bound access tokens through:

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `GET /api/v1/auth/me`
- `POST /api/v1/auth/logout`
- `POST /api/v1/auth/logout-all`

Create the Passport personal-access client once per environment:

```bash
docker compose exec -T milog-phpfpm php artisan passport:client --personal --provider=users --name="MiLog UI"
```

Production also requires `MILOG_PASSPORT_PRIVATE_KEY_B64` and
`MILOG_PASSPORT_PUBLIC_KEY_B64`. Set them to the base64-encoded output of the
environment's Passport signing keys; signing keys are excluded from production
images.

Grant an existing user access to a tenant:

```bash
docker compose exec -T milog-phpfpm php artisan milog:grant-tenant user@example.com TENANT_UUID --role=member
```

For direct PostgreSQL administration, the equivalent idempotent upsert is
available at [`database/sql/upsert_tenant_user.sql`](database/sql/upsert_tenant_user.sql).
It accepts `user_email`, `tenant_id`, and `tenant_role` as `psql` variables.

Access tokens are short lived. Refresh tokens rotate on every use, are stored
only as hashes, and remain bound to their original tenant. Reusing a rotated
refresh token revokes the entire session family. UI logout does not revoke
producer `X-API-Key` credentials.

The complete client contract is in
[`docs/ui-api.oas.yaml`](docs/ui-api.oas.yaml).

## Production Images

The default `docker-compose.yml` is for local development. Production uses
`docker-compose.production.yml`, immutable application images, internal data
services, health checks, persistent named volumes, and Compose secrets.

Build release images with a unique release tag:

```bash
docker build -f docker/php-fpm/production.Dockerfile -t registry.example.com/milog-api/php:RELEASE .
docker build -f docker/nginx/production.Dockerfile -t registry.example.com/milog-api/nginx:RELEASE .
```

Provide the required values shown in `docker/production.env.example` through
the deployment environment, then validate and start the production topology:

```bash
docker compose --env-file docker/production.env -f docker-compose.production.yml config --quiet
docker compose --env-file docker/production.env -f docker-compose.production.yml up -d
```

Terminate TLS at the load balancer or ingress in front of the production Nginx
container. PostgreSQL and Redis have no host-published ports.

## Project Notes

- PostgreSQL is the primary application database.
- Redis is available for future queue and enrichment work.
- The formatter layer is intentionally extensible.
- The event model is append-only by design.
